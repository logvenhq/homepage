The idea

Logven is a tool for defining, running, observing, and formalizing enterprise and business operations, built to tackle the grey-area work of enterprise technical teams.

The problem

Companies are often asked to map out an entire process before doing anything. In practice, the dependencies, weird exceptions, approvals, and edge cases are exactly what nobody has been able to define upfront.

Everyone has this funny little problem of having to develop useful frameworks for 20k+ employees. In enterprise, this is quite necessary. Having everything on-prem is also a recurring concern.

The solution

The idea is pretty simple: instead of asking a company to map out an entire process before doing anything, you let LLM-powered agents do the work first. Then you look at how the work actually happened.

An initial agent is basically a hypothesis about how a piece of work should be done. It’s useful because you can run it, see where it breaks, and learn from that. You begin with a rough version of the process, run it on real work, and gradually figure out what was missing.

Over time, those executions give you enough information to turn messy workflows into standard processes, and eventually into actual custom software built around that operation.

In the end, user-modelled agents are just the starting shape. What you actually want is for them to slowly turn into custom software for the company: private, mostly deterministic, and using small LLMs only where they are genuinely useful, ideally under 40B parameters.

I hate all the agentic slop wave we have now in 2026. This was, to me, one of the few uses of the agentic concept that actually made sense: agents as something temporary. You use them to get the work running and understand the operation, then you replace the stable parts with normal software.

An example

A real example is something I had the chance to discuss with a geothermal team in the public sector, at ARPAT.

They manage data from 36 geothermal plants. The work is basically a mix of extracting values from PDFs, updating spreadsheets and databases, combining and analyzing data, writing reports, reading responses, and dealing with anomalies.

Maybe five plant-specific agents are actually doing the exact same thing.

Maybe one plant has a weird exception.

Maybe operators always correct the same field after PDF extraction.

Maybe the same three anomaly types keep appearing.

Maybe a step everyone thought needed an LLM is actually completely deterministic.

As the system sees more executions, Logven can start merging equivalent agents, defining common data formats, adding approval steps where they’re actually needed, and replacing unstable agent handoffs with normal code and integrations.

The model stays only in the parts where ambiguity is still present.

Eventually, what you have isn’t really an agent system anymore. It’s a plant-operations system that converged from the work itself instead of being fully designed upfront.

And that’s vanilla software, not AI slop, so quite cheap too.

Team

Logven is being built closely with the technical teams who will use it. The product is shaped through direct conversations, real workflows, and early implementations in hard-tech environments.

The team is small for now, and the work is deliberately close to the operations it is meant to improve.

Collaborations

These collaborations are where the product becomes concrete: real operations, real constraints, and a direct view of what should become software next.
